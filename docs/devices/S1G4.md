## Before you start

Check first:

- [ ] the device runs Shelly's own firmware, not ESPHome yet
- [ ] you know its IP address (`--ip`), or this PC is on the device's own access point (default `192.168.33.1`)
- [ ] the device can reach this PC: same network, port 8000 (`--port`) not blocked
- [ ] your ESPHome config uses the partition table below and is compiled
- [ ] a UART adapter is at hand as your way back ([Recovery over UART](../recovery-uart.md))

## ESPHome config

> [!IMPORTANT]
> `build` refuses a config without Shelly's partition table. Copy `partitions/S1G4-stock.csv` from this repository next to your
> YAML and keep `CONFIG_PARTITION_TABLE_OFFSET: "0x10000"`.

```yaml
esp32:
  variant: ESP32C6
  board: esp32-c6-devkitc-1
  flash_size: 8MB
  partitions: S1G4-stock.csv        # copy from partitions/ in this repository
  framework:
    type: esp-idf
    sdkconfig_options:
      CONFIG_PARTITION_TABLE_OFFSET: "0x10000"
    advanced:
      enable_ota_rollback: false

ota:
  - platform: esphome
    allow_partition_access: true
```

The C6 needs the 80 MHz flash header, otherwise `build` refuses to replace the bootloader. If it complains, add under `esphome:`:

```yaml
esphome:
  platformio_options:
    board_build.flash_mode: dio
    board_build.f_flash: 80000000L
    board_build.flash_size: 8MB
```

> [!TIP]
> The [ESPHome device page](https://devices.esphome.io/devices/shelly-1-gen4/) has a config to start from. Replace its `esp32:` block with the one above, or `build` refuses it.

## Pins

| Function | Pin |
| --- | --- |
| Relay | GPIO5 |
| Switch input (SW) | GPIO10 |
| Button (pull-up, inverted) | GPIO4 |
| Internal temperature sensor | works (no pin) |
| Status LED (red, active low) | GPIO15, `inverted: true` |

Source: a device report ([#130](https://github.com/oxynatOr/free-shelly-ota/issues/130)) that tried relay, switch input, button and temperature on four units under ESPHome. The LED pin was tried on a second unit with a plain `output` + `light` on GPIO15 and on GPIO0, toggled one by one: GPIO15 is the red status LED, active low (output on = LED off); GPIO0 has no visible LED. The [ESPHome device page](https://devices.esphome.io/devices/shelly-1-gen4/) says GPIO0, which is wrong for this board. A working status LED:

```yaml
status_led:
  pin:
    number: GPIO15
    inverted: true
    ignore_strapping_warning: true
```

> [!IMPORTANT]
> **Pad hold: the relay may not react after the update.** Right after the OTA conversion the relay did not react at all (reset reason `software via esp_restart`). Shelly OS leaves the pad hold enabled on GPIO5, GPIO10 and GPIO15, and the update only soft-resets the chip, so the hold survives into ESPHome. Either power-cycle the device once, or release the holds at boot. A unit on a permanent 12 V supply never gets a power cycle, so the reporter put this into every config:
>
> ```yaml
> esphome:
>   on_boot:
>     priority: 1000
>     then:
>       - lambda: |-
>           gpio_hold_dis(GPIO_NUM_5);
>           gpio_hold_dis(GPIO_NUM_10);
>           gpio_hold_dis(GPIO_NUM_15);
> ```

## Flash it

1. **Install the requirements** (once):

   ```
   pip install -r requirements.txt
   ```

2. **Fetch** the official package:

   ```
   python ota.py fetch S1G4 --insecure
   ```

3. **Build:** put your app into it; the ZIP goes to `out/`:

   ```
   python ota.py build S1G4 app.ota.bin --esphome-factory app.factory.bin --esphome-yaml app.yaml
   ```

4. **Check the device** first. Nothing is sent:

   ```
   python ota.py send S1G4 out/S1G4-app-<date>.zip --ip <device IP> --dry-run
   ```

5. **Flash it** and watch the log:

   ```
   python ota.py send S1G4 out/S1G4-app-<date>.zip --ip <device IP> --watch 120
   ```

`app.ota.bin` and `app.factory.bin` are the two files ESPHome compiles. `--dry-run` only checks the device and, for this
package, reads the update target slot. Command reference: [Commands](../commands.md).

## What to expect

In the `--watch` log look for these lines, in this order:

| # | Log line | Meaning |
| --- | --- | --- |
| 1 | `Update target slot: 0 ...` | The slot check of `send`. Anything else: run `python ota.py restore S1G4` first |
| 2 | `Boot: cur ... min ... update? 1` | The installer will write ESPHome's bootloader. `update? 0` means it will not: build again with a higher `--boot-min-version` ([why](../bootloader-and-slots.md#is-the-new-bootloader-really-written-min_version)) |
| 3 | `ota_progress` up to 95 %, then `ota_success` | The device restarts into ESPHome |

## Notes for this device

- **Result:** first report ([#130](https://github.com/oxynatOr/free-shelly-ota/issues/130), thanks to [CzarofAK](https://github.com/CzarofAK)), from stock **2.0.3** with the package built from this profile (revision 2, package 2.0.3, `--esphome-factory`). `send` read the update target slot 0 (the device itself reported slot 1), the device reached the PC at -40 dBm, the flash ran to 100 % and the device restarted into ESPHome. A later ESPHome OTA took effect (slot 0 -> 1 -> 0), so ESPHome's bootloader is in place.
- **Loader 1.0.3 on stock 2.0.3:** `Boot: cur 010003ff, new 00000000, min 010009ff, update? 1`, so `boot_min_version: 1.0.9` made the installer write ESPHome's bootloader (`Installing BL 21760@app_0(0x20000) -> boot(0)`). The log then shows `Will write to slot 0` and the usual `efuse ... Write operation is forbidden` lines, which did no harm.
- **Checked on hardware:** relay, switch input, button and the internal temperature sensor work, on the converted bench unit and on two more units that are now installed. In total four 1 Gen4 units were converted on one day, all from stock 2.0.3, all with ESPHome's bootloader written and a working ESPHome OTA afterwards.
- **Config used:** the `esp32:` block of this page was accepted by `build` without extra flash options (the reporter also set `CONFIG_ESPTOOLPY_FLASHFREQ_80M: "y"`). The status LED was checked on a second unit (`shelly-fountain`, flashed with 0.7.0, ESPHome 2026.10.2): GPIO15 inverted, see [Pins](#pins); two ESPHome builder OTAs on that unit went through, so the slot switching works there as well.
- **Zigbee firmware:** one unit reported `S1G4ZB` (Shelly's Zigbee firmware variant of the same hardware, like `Mini1PMG4ZB`) in a first check and `S1G4` in the next. After `restore S1G4`, run twice to move the running slot from 0 to 1, it went through like the others.

The profile sets `boot_min_version: "1.0.9"`: devices of this family run Shelly's loader 1.0.3, which would otherwise skip ESPHome's bootloader (`update? 0`).

## Way back

`python ota.py restore S1G4` sends the official firmware back while Shelly firmware still runs.

---

> [!WARNING]
> - **Wipes Wi-Fi and settings.** ESPHome opens its own access point or joins the Wi-Fi from your config; if nothing comes up, power-cycle the device ([help](../troubleshooting.md#esphome-does-not-start-after-the-update)).
> - **No way back over the network** once ESPHome's bootloader runs: `restore` gets no answer, only UART brings Shelly OS back ([Recovery over UART](../recovery-uart.md)). Take a flash backup first if you can.
> - **Flashed it? Tell us,** also when it worked: [open a device report](https://github.com/oxynatOr/free-shelly-ota/issues/new?template=device-report.yml).
